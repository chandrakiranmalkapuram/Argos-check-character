# Voice Confusion Engine Specification & Documentation

The **Voice Confusion Engine** is an independent, deterministic algorithmic module that identifies and ranks confusable warehouse location codes for voice-directed picking systems.

---

## 1. Core Philosophy & The Same-Check Gate (Invariant I2)

In voice picking environments, operatives use headsets to receive pick instructions and must verbally confirm shelf locations. The check character is a NATO word (ALPHA to ZULU) calculated per location, which the headset software requests after the location is entered.

- **Different-check codes**: If an operative mishears or mispronounces a location whose true check character differs from the intended location, the headset voice recognition software would normally reject the verification check. The picker cannot confirm the pick and is prompted to repeat or re-read the location.
- **Same-check pairs**: If two distinct location codes produce the **exact same check character**, the error is not caught by the check-character step if the confusion occurred.

### The Same-Check Invariant (I2)
> **Every candidate suggested in Tier 1 (Reported), Tier 2 (Model-Similar), Tier 3 (Possible), and Section (d) (Arithmetic Pool) MUST share the identical check character of the searched location.**

Any community report where the reported code has a *different* check character is strictly partitioned into **Section (e)** (*"Reported confusions with a different check character: the headset would normally reject these"*). It is never permitted into the ranked candidate tiers.

## 2. Candidate Tiers & Real Classification Function

Candidate locations are generated by scanning valid location codes in the warehouse grammar and filtered against the same-check gate.

The engine classifies alignment tiers using `classifyAlignmentTier` from `src/logic/voiceConfusion/engine.ts`:

```typescript
export function classifyAlignmentTier(
  alignment: TokenAlignmentPair[],
  options?: {
    maxDiffTier2?: number;
    maxDiffTier3?: number;
    maxFarDistTier3?: number;
    qualifiesForTier1?: boolean;
  }
): AlignmentClassificationResult {
  const maxDiffTier2 = options?.maxDiffTier2 ?? MAX_DIFFERING_TOKENS_TIER2;
  const maxDiffTier3 = options?.maxDiffTier3 ?? MAX_DIFFERING_TOKENS_TIER3;
  const maxFarDistTier3 = options?.maxFarDistTier3;

  let farTokens = 0;
  let nearTokens = 0;
  let identicalTokens = 0;
  let singleFarDist = 0;
  let totalDistance = 0;

  for (const pair of alignment) {
    totalDistance += pair.distance;
    if (pair.distance === 0) {
      identicalTokens++;
    } else if (pair.distance <= MODEL_SIMILAR_TOKEN_THRESHOLD) {
      nearTokens++;
    } else {
      farTokens++;
      singleFarDist = pair.distance;
    }
  }

  const differingTokens = nearTokens + farTokens;

  // Tier 2: Model-Similar: 0 far tokens (all differing tokens are model-similar <= 0.55)
  // and total differing tokens <= maxDiffTier2
  const isTier2 = farTokens === 0 && differingTokens <= maxDiffTier2;

  // Tier 3: Possible: exactly 1 far token, total differing tokens <= maxDiffTier3,
  // and far token distance <= maxFarDistTier3 (if specified)
  const isTier3 =
    farTokens === 1 &&
    differingTokens <= maxDiffTier3 &&
    (maxFarDistTier3 === undefined || singleFarDist <= maxFarDistTier3);

  let tier: CandidateTier;
  if (options?.qualifiesForTier1) {
    tier = 'tier1_reported';
  } else if (isTier2) {
    tier = 'tier2_model_similar';
  } else if (isTier3) {
    tier = 'tier3_possible';
  } else {
    tier = 'arithmetic_collision';
  }

  return {
    tier,
    identicalTokens,
    nearTokens,
    farTokens,
    differingTokens,
    singleFarDist,
    totalDistance
  };
}
```

### Classification Rules Summary

| Tier | Name | Criteria | Configuration Defaults |
| :--- | :--- | :--- | :--- |
| **Tier 1** | **Reported & Verified** | Verified community or moderator report sharing the same check character, with an acoustic reason (`similar_sounding` or `headset_misrecognition`) and status `approved`/`confirmed` (or provenance `moderator_confirmed` with `community_submitted`). | Elevated above algorithmic ranking. |
| **Tier 2** | **Model-Similar** | 0 far tokens (all differing tokens have pairwise distance $\le \text{MODEL\_SIMILAR\_TOKEN\_THRESHOLD}$, which is $0.55$) and total differing tokens $\le \text{MAX\_DIFFERING\_TOKENS\_TIER2}$. | `farTokens === 0`, `differingTokens <= 2`. |
| **Tier 3** | **Possible Sound-Alikes** | Exactly 1 far token (pairwise distance $> 0.55$), total differing tokens $\le \text{MAX\_DIFFERING\_TOKENS\_TIER3}$. (An optional ceiling `maxFarTokenDistanceTier3` exists in the code but is disabled by default). | `farTokens === 1`, `differingTokens <= 2`. |
| **Pool** | **All Same-Check Codes (Arithmetic Pool)** | Remaining same-check codes that do not qualify for Tiers 1–3 (e.g., more than 1 far token, or total differing tokens $> 2$). | Computed lazily upon disclosure toggle. |

## 3. Near Threshold Convention (`MODEL_SIMILAR_TOKEN_THRESHOLD = 0.55`)

Spoken tokens are compared pairwise using an articulatory phonetic feature comparator based on place, manner, voicing, and vowel height/backness.

- **Acoustic Distance $= 0.0$ (`identical`)**: Exact phonetic match (e.g., `ALPHA` vs `ALPHA`).
- **Acoustic Distance $\le 0.55$ (`near / model-similar`)**: Values printed from the precomputed token distance table:
  - `WHISKEY` / `YANKEE` = 0.3500
  - `ALPHA` / `DELTA` = 0.4000
  - `DELTA` / `TANGO` = 0.5100
  - `BRAVO` / `PAPA` = 0.5200
- **Acoustic Distance $> 0.55$ (`far`)**: Distinct phonetic tokens:
  - `KILO` / `LIMA` = 0.6250
  - `JEWELLERY` / `ZERO` = 0.6600
  - `ECHO` / `BRAVO` = 0.7000
  - `ZERO` / `NINE` = 0.7000
  - `ALPHA` / `HOTEL` = 0.8000
  - `ALPHA` / `ZULU` = 0.9000
  - `TWO` / `ONE` = 0.9333
- **Token Gap Cost $= 0.90$**: Penalty applied in Needleman-Wunsch gapped alignments when aligning unequal token sequences.

## 4. Pronunciation Lexicon Assumptions

1. **NATO Phonetic Alphabet**: Letters are vocalised using NATO standard words:
   `A` = ALPHA, `B` = BRAVO, `C` = CHARLIE, ..., `Z` = ZULU.
2. **Digit-by-Digit Vocalisation**: Numbers are vocalised digit-by-digit:
   - Aisle `10` is spoken as `"ONE ZERO"`, **never** as `"TEN"`.
   - Aisle `08` is spoken as `"ZERO EIGHT"`.
3. **Prefix Map Disambiguation**: In store locations, special prefix letters at index 0 indicate departments (e.g., `J` = `"JEWELLERY"`), which has distance 0.6600 with `"ZERO"`.

## 5. Evidence Rules (Decisions D3, D9, D11)

- **Decision D3 (Reference Example Badge)**:
  The seven reference seed rows carry provenance `seed_observation` and are labelled with a distinct **Reference example** badge. Seed observations alone do not elevate uncorroborated candidates into Tier 1 without independent community approval.
- **Decision D9 (Reported Pairs Section)**:
  Section (a) lists reported confusion pairs for the active location. Directionality is isolated: reports where location $A$ was misrecognised as $B$ are displayed when viewing $A$.
- **Decision D11 (Acoustic Reason & Status Gate)**:
  Only reports with acoustic reasons (`similar_sounding` or `headset_misrecognition`) combined with status `approved` or `confirmed` (or provenance `moderator_confirmed` with status `community_submitted`) may elevate a candidate to Tier 1. Reports with reason `similar_check_character` or `other` appear in the reported list with the disclaimer *"Reported (layout / check-character), does not affect ranking"*, preventing non-acoustic submissions from skewing phonetic rankings. Disallowed statuses (`flagged`, `rejected`, `archived`, `pending`) never elevate.

## 6. Supported Grammar & Unsupported Inputs

The engine operates strictly on 4-character warehouse location codes conformant with the four recognised Store patterns:
1. **Standard aisle**: `[0-9]{2}[A-Z]{2}` (e.g. `10AK`)
2. **Jewellery / Security**: `[JS][0-9][A-Z]{2}` (e.g. `J7AZ`, `S1PG`)
3. **Linbin / Bulk**: `[LZ][0-9]{2}[A-Z]` (e.g. `L01B`, `Z01B`)
4. **Cash Office / Collection Point**: `C[AP][0-9]{2}` (e.g. `CA01`, `CP99`)

### Unsupported Inputs and Typed Reasons (`UnsupportedReason`)

Inputs rejected by the grammar parser produce typed reasons:
- `relative_marker`: Codes ending in relative level symbols (e.g. `10A+`, `10A-`).
- `fixed_code`: Fixed warehouse functional codes with hardcoded check characters (e.g. `DPA`, `SOB`).
- `returns_alias`: Special returns aliases (e.g. `RET1`).
- `rfc_candidate`: Regional Fulfilment Centre locations using the 6-character RFC algorithm (e.g. `LAKE`, `ABCD`).
- `invalid_format`: Strings exceeding 4 characters (e.g. `10AKX`), empty strings, whitespace, punctuation, or non-grammar patterns.

## 7. Known Assumptions & Areas Needing Validation

1. **Hand-Authored Lexicon Pronunciations**: Token pronunciations are defined statically in `src/logic/voiceConfusion/phonetics/lexicon.ts`. Variations in regional accents and headset synthesis are not modeled.
2. **Headset Vocabulary & Recognition Behaviour Unknown**: The exact internal acoustic models, grammar constraints, language models, and rejection thresholds of commercial voice picking headsets are proprietary and unknown.
3. **Letter-Name Mode Disabled**: Tokens assume standard NATO code words. Letter-name pronunciation mode (`A` = "ay", `B` = "bee") is disabled by default.
4. **Grammar is Theoretical**: The 86,520 locations represent all syntactically valid codes under the Store grammar. There is no store planogram or inventory verification; every candidate is a possible code, not verified to exist in your store.
5. **Tier Caps & Near Threshold are Conventions**: The near threshold (`0.55`) and the 2-token difference caps are heuristic engineering conventions under the hypothesis of independent token errors.
6. **Independent Token Error Assumption**: Positional and gapped comparators assume token errors occur independently across positions without modeling co-articulation or acoustic masking across syllables.
7. **Seeds are Reference Examples Without Negatives**: The seven seed rows represent reference examples (`seed_observation`). There are no curated negative controls (non-confused same-check pairs) in the baseline dataset.
8. **Report Independence Only via `client_hash`**: Community corroborations are tracked per `client_hash`. If multiple operatives submit from a shared terminal, independence cannot be guaranteed.
9. **No Real Headset Audio Data**: No live headset audio streams, background noise recordings, or ASR acoustic log-likelihood scores were collected.

### Adding Benchmark Cases
To add new benchmark cases (such as new field observations, negative controls, or alternate acoustic pairs):
1. Open `benchmarks/voice_confusion_benchmark.jsonl`.
2. Append a valid JSON object line:
   ```json
   {"a":"16ZG","b":"16CZ","mode":"store","source":"community_report","confused":true}
   ```
3. Execute the benchmark runner:
   ```bash
   npm run benchmark:voice
   ```
